# 🌐 Listen Server 채택 이유

> **결정**: 본 프로젝트는 **Listen Server + Steam Online Subsystem** 방식으로 멀티플레이를 구현한다.
> **대안 검토**: Dedicated Server (자체 서버 호스팅 방식)
> **결정일**: 2026-05-03

---

## 📌 1. 결론 요약

**한 줄 요약**: 포트폴리오 단계에서는 자체 서버 운영 부담 없이 멀티플레이를 완성도 있게 구현·시연할 수 있는 **Listen Server + Steam** 방식이 최적이다.

핵심 원칙: *"Listen Server로 구현하되, 모든 게임 로직은 Dedicated Server로도 전환 가능하게 권한 분리(`HasAuthority` + Server RPC)를 정확히 지킨다."*

---

## 🎯 2. Listen Server란?

방장(Host) PC가 **서버 + 클라이언트 역할을 동시에** 수행하는 구조.

```
[방장 PC = 서버 + 클라이언트]
       ↑
   ┌───┼───┐
   │   │   │
[친구1][친구2][친구3]
   클라  클라  클라
```

방장이 방을 만들면, 다른 플레이어들은 방장 PC에 직접 접속하여 게임을 진행한다.
**Among Us, Valheim, Minecraft** 등 다수의 멀티 게임이 이 구조를 사용.

---

## ✅ 3. 채택 이유

### 3.1 자체 서버 비용·운영 부담 0
- Dedicated Server는 **클라우드 호스팅 비용** (AWS GameLift, Edgegap 등)이 매월 발생
- 포트폴리오 단계에서는 **상시 서버 유지가 비현실적**
- Listen Server는 방장 PC가 곧 서버이므로 **추가 인프라 불필요**

### 3.2 시연(포트폴리오) 친화적
- Dedicated Server는 *"면접 끝나면 서버 내려야 함"* 의 문제 발생
- Listen Server는 **언제든 본인이 게임만 켜면 작동** → 시연·발표·재현 용이
- 평가자가 직접 다운받아 친구와 플레이해보는 것도 가능

### 3.3 Steam Online Subsystem과의 시너지
Steamworks SDK가 제공하는 무료 기능을 그대로 활용:

| 기능 | 효과 |
|------|------|
| **NAT 펀치스루** | 포트포워딩 없이 친구 PC와 연결 가능 |
| **릴레이 서버** | 직접 연결 실패 시 스팀이 중계 |
| **로비 시스템** | 방 만들기·입장·검색 |
| **친구 초대** | 스팀 친구창에서 클릭 한 번 |
| **유저 인증** | Steam ID로 로그인 처리 |

→ 자체 서버 없이도 **인터넷 너머 친구들과 멀티플레이가 가능**해진다.

### 3.4 비용 효율성
- Steamworks 가입비: **게임당 $100 (1회성, 정식 출시 시점에만 필요)**
- 개발 단계: **App ID 480 (Spacewar)** 으로 무료 무제한 테스트
- 운영 비용: **0원**

### 3.5 언리얼 엔진 표준 지원
- Online Subsystem Steam은 **언리얼 기본 내장 플러그인**
- Listen Server 모드 역시 언리얼이 표준으로 지원
- 별도의 외부 솔루션 없이 엔진 기능만으로 구현 가능

### 3.6 개발 난이도 단순화
- Dedicated Server는 **별도 서버 빌드, 매치메이킹 시스템, 클라우드 인프라**가 필수
- Listen Server는 **클라이언트 빌드 하나로 호스트·게스트 모두 처리**
- 핵심 게임 로직 개발에 집중할 수 있는 환경 확보

## ⚠️ 4. Listen Server의 한계 (인지하고 있는 단점)

| 단점 | 설명 | 영향도 |
|------|------|--------|
| **호스트 어드밴티지** | 방장은 핑 0, 다른 플레이어는 핑 발생 | 포폴 단계에선 무관 |
| **방장 이탈 시 게임 종료** | 또는 호스트 마이그레이션 필요 | 운영 시 보완 필요 |
| **치팅 위험성** | 서버 권한이 방장 PC에 있음 | 포폴 단계에선 무관 |
| **방장 PC 사양 의존** | 방장 PC 성능이 모두에게 영향 | 친구 간 플레이 시 협의 |

이 한계점들은 **포트폴리오 단계의 목적**(게임 디자인·코드 품질 시연)에서는 결정적 문제가 아니며, 추후 Dedicated Server 전환 시 자연스럽게 해결된다.

---

## 🔄 5. 추후 Dedicated Server 전환 가능성

### 5.1 전환의 용이성
언리얼은 Listen Server / Dedicated Server **동일 코드 베이스**를 공유:
- `HasAuthority()` 권한 체크
- `Server` / `Client` / `Multicast` RPC
- Replication 시스템

→ **게임 로직 코드는 거의 그대로 재사용 가능**.

### 5.2 처음부터 지킬 핵심 원칙
모든 게임 로직은 **반드시 서버 권한 검증 후 실행**:

```cpp
// ❌ 나쁜 예 (클라가 직접 결정)
void APlayerCharacter::Attack() {
    OtherPlayer->Health -= 10;
}

// ✅ 좋은 예 (서버에 요청)
void APlayerCharacter::Attack() {
    Server_Attack();
}

void APlayerCharacter::Server_Attack_Implementation() {
    if (HasAuthority()) {
        OtherPlayer->Health -= 10;
    }
}
```

이 원칙을 지키면 Listen → Dedicated 전환 시 **게임 로직 재작성 없이 인프라 작업만으로 마이그레이션 가능**.

### 5.3 전환 시 추가 작업 추정

| 작업 | 예상 기간 |
|------|-----------|
| Dedicated Server 빌드 설정 | 1~2주 |
| 서버 / 클라 코드 분리 (UI·렌더링 등) | 2~4주 |
| 매치메이킹 시스템 구축 | 4~8주 |
| 클라우드 호스팅 인프라 | 2~4주 |
| **총합** | **약 2~4개월** |

→ 전환 자체가 어려운 작업이 아니며, **포트폴리오 v2 / v3 의 발전 방향**으로 자연스럽게 이어진다.

## 📊 6. 비교 정리표

| 항목 | Dedicated Server | **Listen Server + Steam (채택)** |
|------|------------------|----------------------------------|
| 자체 서버 비용 | 월 수만 원~ | **0원** |
| 운영 부담 | 서버 관리·모니터링 필요 | **거의 없음** |
| 개발 난이도 | 높음 | **낮음** |
| 친구와 테스트 | IP 공유 또는 클라우드 필요 | **스팀 친구창 클릭** |
| 치팅 방지 | 강함 | 약함 |
| 포트폴리오 시연 | 서버 상시 운영 부담 | **언제든 즉시 시연** |
| 정식 출시 적합성 | ✅ | △ (전환 권장) |

## 🎯 7. 결정 요지

> **"포트폴리오 단계의 목적은 게임 디자인과 멀티 동기화의 작동을 증명하는 것이지, 상용 서비스 인프라를 구축하는 것이 아니다."**

이에 따라:
1. **Listen Server + Steam Online Subsystem**으로 멀티플레이를 구현한다.
2. 모든 게임 로직은 **`HasAuthority()` + Server RPC 패턴**을 엄격히 준수한다.
3. 추후 필요 시 Dedicated Server로 전환할 수 있는 **확장성 있는 코드 구조**를 유지한다.
